# Финансовый отчёт из локального LibreOffice Calc

Рабочая задача и критерии готовности: [Issue #1](https://github.com/Ishayahu/jewish-chrono/issues/1).

**Состояние:** подготовленный скрипт; НЕ переключён на локальные данные. Пока обновления сайта по-прежнему формируются текущим GitHub Actions из Google Sheets. **Не устанавливать `PUBLISH_ENABLED=True` до сверки данных и замены workflow!**

## Что сделано

- [`publish_from_calc.py`](publish_from_calc.py) читает сохранённые значения ячеек **.ods** и **.xlsx** через `python-calamine` и формирует JSON той же структуры, что нынешний зашифрованный дашборд.
- В самом верху скрипта указываются `WORKBOOK_PATH`, `CELLS` (лист + адрес), `RUB_DEBTS`, `CHILDREN`, `INSTALLMENTS`, `CYCLES`, `BUDGET_ROWS`. Ниже этой секции код менять не нужно.
- Шаблон ожидает три цикла и их лимиты/фактические расходы. Для подписок в USD создаётся отдельная информационная статья, не повторно включаемая в RUB-расходы.
- Публикация формирует два независимых AES-256-GCM отчёта с PBKDF2-SHA256 / 600000 итераций: `finance/data/owner.enc` и `finance/data/family.enc`. Открытые суммы и сам .ods **никогда не передаются** в GitHub.
- GitHub-загрузка выполняется **одним атомарным коммитом** двух зашифрованных файлов, с запретом перезаписи чужого нового коммита.

## Первоначальная настройка на компьютере

1. Установить Python 3.11+ и библиотеки:

   ```powershell
   py -m pip install python-calamine cryptography
   ```

2. Открыть локальную книгу в LibreOffice Calc. Для простоты можно создать отдельный лист **«Экспорт»** с формулами-ссылками на уже существующие ячейки других листов. Это **не второй журнал** и не второй расчёт, только витрина готовых показателей.

3. На листе «Экспорт» примерная раскладка:
   - B2–B11: исторический/прогнозный дефицит, служебный баланс, остаток ГМАХ USD, сценарный курс, фактические накопления, теоретический резерв, зафиксированная дневная цель, дневное поступление и сумма неклассифицированных расходов. **B11 должен содержать реальное 0**, если таких расходов нет.
   - B12–B15: четыре долга в RUB; B17–B19: накопления детям; B21:C22: число платежей и сумма за платёж двух рассрочек.
   - B25/B26/B27: название, доступный прогнозный доход и **общий RUB-план расходов** текущего цикла. D25:D27 и F25:F27 — аналогично для следующих двух циклов.
   - B32:C48: лимит/факт категорий текущего цикла, D32:E48 и F32:G48 — те же категории следующих двух циклов. Строки 32–48 по названиям перечислены в `BUDGET_ROWS` в начале скрипта.
   - Строка 48 «Подписки (USD-резерв)» — сумма **эквивалента резервируемых USD по сценарию**, в RUB-расходы не включается повторно. Валютные резервы уже уменьшили доход в расчёте Calc.
   - Будущие циклы без расходов должны иметь **числовое 0** в колонке факта, а не пустую ячейку.

4. В начале скрипта изменить `WORKBOOK_PATH`, имена листов и адреса ячеек. Если данные лежат не в общей таблице категорий, использовать `BUDGET_CELL_OVERRIDES`: на любую категорию и цикл можно назначить индивидуальные ссылки. **Никаких реальных адресов локального файла мы пока не знаем; «Экспорт» — проектная раскладка.**

5. Сохранить книгу в LibreOffice **перед экспортом**, иначе скрипт может прочитать старые результаты формул: `python-calamine` не пересчитывает формулы самостоятельно.

6. Проверить командой из каталога репозитория:

   ```powershell
   py finance/publish_from_calc.py --book "C:\Users\...\Documents\budget.ods"
   ```

   Это режим `dry-run` по умолчанию: проверяет значения и формат отчёта, но **ничего не отправляет** в GitHub. При пустой или неверной ячейке немедленно остановится с её адресом.

7. При желании проверить полноценное шифрование и получить **только локальные зашифрованные файлы**:

   ```powershell
   $env:FINANCE_OWNER_PASSWORD = Read-Host "Пароль дашборда"
   $env:WIFE_PASSWORD = Read-Host "Пароль семейного отчёта"
   py finance/publish_from_calc.py --export-only
   ```

   Пароли не вписывать в файл или в GitHub. Использовать надёжные уникальные пароли (скрипт требует не менее 16 символов). **Проверьте совместимость существующих сохранённых паролей; при смене пароля повторно авторизоваться на сайте.** По умолчанию `.enc` сохраняются только локально. Точное место задаёт `--output-dir`.

## Только после прохождения сверки

- Сравнить числа в Calc и действующем отчёте: 3 цикла, суммарные лимиты, доходы, прогнозный дефицит и отдельный исторический снимок, дневная цель, накопления, долги. Программа проверяет некоторые инварианты, но **не может доказать экономическую корректность формул Calc**.
- Переписать `.github/workflows/finance.yml` на развёртывание **готовых зашифрованных файлов**, больше не вызывать `finance/build_encrypted.py` и Google API. Подтвердить тестовую публикацию.
- Только после этого поставить `PUBLISH_ENABLED = True` в настройках скрипта, задать токен fine-grained GitHub PAT с доступом **Contents: write** к **только этому репозиторию** и вызвать:

  ```powershell
  $env:GITHUB_TOKEN = Read-Host "GitHub token"
  py finance/publish_from_calc.py --publish
  ```

- При включённом старом workflow скрипт **откажется публиковать**, даже если `PUBLISH_ENABLED=True`. Если кто-то одновременно обновит ветку, атомарный push завершится ошибкой без force-push: данные не перезапишутся.
- Дашборд покажет время последнего **сохранения локальной книги**, а не кажущуюся «свежесть» публикации. Когда ПК выключен, опубликованный отчёт остаётся прежним.

## Ограничения

- Скрипт **не редактирует** Calc, не импортирует операции из ChatGPT и не переносит старую историю.
- Ему нужны числовые итоги, уже рассчитанные формулами локальной таблицы. Если значения не представлены соответствующими ячейками, их надо добавить в таблицу или в лист «Экспорт».
- Оплата рассрочек/кредиторов должна влиять на остатки только по факту, а переводы между своими счетами не должны превращаться в новый доход/расход.
- Зашифрованные файлы сохраняются в истории публичного GitHub. Слабый пароль может быть атакован офлайн, поэтому пароль нужен действительно сильный. Для критичных данных предпочтительно приватное распространение или отдельно проверенная схема секретов; сам .ods и пароль публично не размещать.
