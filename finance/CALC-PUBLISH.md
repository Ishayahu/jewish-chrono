# Локальный Calc → зашифрованный финансовый дашборд

**Состояние 23.11.2026:** скрипт и автоматические проверки обновлены, **фактическая публикация из Calc пока не включена**. Для Windows добавлен готовый запуск `finance/run_calc_export.cmd` — пользователь не обязан набирать команды и задавать пароли через PowerShell. Рабочая задача: [Issue #1](https://github.com/Ishayahu/jewish-chrono/issues/1). Старый workflow по-прежнему собирает сайт из Google Sheets. Это намеренная защита: нельзя одновременно позволять двум процессам перезаписывать финансовый отчёт.

## Источник и структура

- Источник: сохранённый локальный файл LibreOffice **.ods**, лист `Семейные Траты`. Внешний лист «Экспорт» **больше не нужен**.
- Текущий и следующие два финансовых цикла находятся в 14-строчных блоках. В предоставленном файле: **640–653, 654–667, 668–681**.
- Скрипт динамически ищет текущий цикл по дате в `A640`, затем сдвигается на 14 строк. Дата вида `01.01.2027` означает **цикл 21.12.2026–20.01.2027**, а не календарный январь.
- Левая таблица: `D` — категория, `G` — утверждённый бюджет, `C` — потрачено, `F` — остаток. Последняя строка `ВТОРОЙ СТОЛБЕЦ` — **итог**, а не новая статья.
- Правая таблица: `O` — категория, `R` — бюджет, `N` — потрачено, `Q` — остаток. Служебные `REM` не экспортируются.
- Доходы: `H` — источник; `I` — рубли, `J` — USD. Доход `A[начало+10]` сверяется с суммой **только положительных I + 60 × положительных J**. Базовый бюджетный курс всегда **60 ₽/USD**; фактическая курсовая разница учитывается отдельно при получении денег, не через изменение плана.
- Итого запланированных оставшихся расходов: `A[начало+8]`; доходов: `A[начало+10]`; прогнозного результата с учётом имеющихся в Calc остатков: `A[начало+12]`.
- **Контроль:** сумма остатков уникальных категорий обязана совпадать с `A[начало+8]`, а их `бюджет − факт` обязан совпадать с остатком; иначе публикация отменяется с адресом проблемной строки.

**Проверка исходного файла `Бюджет_2(2).ods`:** эта загруженная версия сохранена *до исправления* двойного включения итога второго столбца и строки `REM`: разница 31 541 ₽ в текущем цикле и 31 920 ₽ в двух следующих. Пользователь сообщил, что исправил локальную версию, однако новая исправленная копия здесь не проверялась. Скрипт специально отклонит старый файл, чтобы не опубликовать неверные суммы.

## Фиксированная дневная цель — БЕЗ макросов Calc

- Скрипт получает из Calc сохранённый **отрицательный** прогноз дефицита в `A[начало+12]`.
- При **первой успешной публикации или локальном экспорте** за московскую дату считает: `max(0, −прогноз дефицита) / (дней до 20-го включительно)`. Округление до копеек. Публикация до получения надёжных данных не производится.
- Цель, дата и исходный прогноз сохраняются в зашифрованном `finance/data/owner.enc` в `dailyGoal` и `goalHistory`. При повторном запуске того же дня скрипт **расшифровывает предыдущий owner.enc и НЕ ПЕРЕСЧИТЫВАЕТ цель**, даже если расходы/доходы Calc изменились. На следующую дату рассчитывает новую цель. Пропущенные дни **не задним числом фиксируются**.
- Для миграции в день переключения сохраняется ранее уже зафиксированная цель из прежнего отчёта, если его дата совпадает с текущей.
- `--publish` читает предыдущее состояние **из GitHub** с фиксацией HEAD; параллельная публикация в ветку не должна перезаписать новую цель. `--export-only` читает предыдущий локальный `owner.enc` из выходного каталога либо `--previous-owner`.
- **ВАЖНО про прежний `owner.enc`:** старый GitHub Actions генерирует `owner.enc` непосредственно при развёртывании сайта и **не коммитит его** в репозиторий. Поэтому архивный [`finance/data/owner.enc`](https://github.com/Ishayahu/jewish-chrono/blob/main/finance/data/owner.enc) может не расшифровываться действующим паролем, хотя сайт открывается. Правильный исходник — [актуальный зашифрованный файл сайта](https://ishayahu.github.io/jewish-chrono/finance/data/owner.enc). Теперь скрипт **автоматически подгружает его** по HTTPS, если файл из репозитория отсутствует либо не открывается действующим паролем. При ошибке расшифровки уже созданного локального `~/finance-export/owner.enc` скрипт **останавливается**, чтобы не затереть ранее зафиксированные цели. Не просить пользователя менять пароль или сбрасывать сайт ради этой ошибки.
- **Ограничение:** при первом запуске дня позднее 05:00 состояние Calc уже может включать сегодняшние операции. Без самостоятельного журнала операций невозможно восстановить точный прогноз *на 05:00*. Поэтому фиксируется сумма **на момент первого фактического запуска**, а не фиктивное «утреннее» состояние. Если ПК выключен, автоматической фиксации в облаке нет.

## Сохранение других показателей

Предоставленный лист надёжно определяет **бюджеты циклов**, но не подтверждает адреса накопленного исторического дефицита, всех долгов, копилок и дневных фактических поступлений. До согласования их локальных адресов эти поля **сохраняются из прежнего зашифрованного `owner.enc`**, с отдельным указанием времени происхождения (`legacyFieldsAsOf`). Скрипт не заменяет их выдуманными нулями. День, для которого нет подтверждённого факта поступлений, отображается как «Нет подтверждённых данных». В `finance/app.js` это специально поддержано.

Скачивать `owner.enc` из репозитория вручную **не требуется**: скрипт берёт шифрованную актуальную копию прямо с сайта, если нужно.

Этот подход **временный**: обновляются именно данные бюджетных циклов и дневная цель. Когда будет проверена привязка остальных показателей к Calc, можно заменить наследование прямым чтением.

## Проверка на компьютере

Python 3.11+, LibreOffice Calc, библиотеки для шифрования и московского часового пояса (особенно для Windows):

```powershell
py -m pip install cryptography tzdata
```

Для `.ods` стандартной библиотеки Python достаточно. Для `.xlsx` дополнительно `py -m pip install python-calamine`.

1. Сохранить свой **уже исправленный** файл в Calc. Скачайте рядом `finance/publish_from_calc.py` и `finance/local_calc_model.py` из данного репозитория.
2. Выполнить пробную сверку; пароль/GitHub не требуются:

   ```powershell
   py finance/publish_from_calc.py --book "C:\Путь\Бюджет_2.ods"
   ```

3. **Для Windows проще дважды щёлкнуть `finance/run_calc_export.cmd`**: он использует `Бюджет_2.ods` и `owner.enc` из `%USERPROFILE%\\OneDrive\\Documents`, при необходимости установит `cryptography`/`tzdata` и сам запросит **существующие** пароли скрытым вводом (только если они не заданы как переменные среды). **Никакого нового ограничения на 16 символов нет**. Пароли, заданные в секретах GitHub Actions, не становятся автоматически переменными среды на локальном ПК. Альтернативно можно запустить вручную:

   ```powershell
   py finance/publish_from_calc.py --book "C:\Путь\Бюджет_2.ods" --export-only --previous-owner "C:\Путь\owner.enc"
   ```

   Файлы `owner.enc` и `family.enc` появятся в `~/finance-export/` **локально**. При повторном `--export-only` предпочтение отдаётся **последнему экспортированному `owner.enc`** из этого каталога, а `--previous-owner` — только исходная резервная копия для первого запуска. Благодаря этому цель того же дня не меняется. **Пароли и токен не записывайте в исходники или в книгу.**

4. **Переключение GitHub Actions подготовлено:** обе сборки (`.github/workflows/finance.yml` и `.github/workflows/pages.yml`) развёртывают **готовые зашифрованные** `finance/data/owner.enc` и `finance/data/family.enc`, как только оба файла появились в одном коммите. До первого локального коммита остаётся старый генератор Google Sheets, поэтому действующий сайт не должен прерываться.

5. **Для первой публикации в Windows** двойным щелчком запустите `finance/run_calc_publish.cmd`. Он сам загружает последние `publish_from_calc.py` и `local_calc_model.py` с `raw.githubusercontent.com/Ishayahu/jewish-chrono`, проверяет синтаксис и использует `%USERPROFILE%\OneDrive\Documents\Бюджет_2.ods`, сохранённую и уже исправленную книгу; последний `~/finance-export/owner.enc` используется для переноса ранее зафиксированной дневной цели. `.ods` никогда не уходит в GitHub.

6. **GitHub авторизация:** программа сначала проверит переменную окружения `GITHUB_TOKEN`, затем работающий вход GitHub CLI (`gh auth login`), а иначе попросит временно ввести токен GitHub скрытым вводом. Fine-grained PAT должен быть ограничен только репозиторием `Ishayahu/jewish-chrono` и правом **Contents: read and write**. Токен и пароли не записывать в Excel/Calc, исходники или переписку.

7. Скрипт выполняет атомарный коммит двух шифротекстов, проверив обе GitHub Actions и не перезаписывая параллельных изменений. Затем на странице GitHub Actions убедиться в успешном развёртывании. Проверить личную панель https://ishayahu.github.io/jewish-chrono/finance/ и семейную https://ishayahu.github.io/jewish-chrono/finance/family/. До подтверждения успешной сборки **не считать, что переключение уже завершено**.

Ручной вариант (если не использовать `.cmd`):

```powershell
py finance/publish_from_calc.py --book "C:\Путь\Бюджет_2.ods" --publish
```

Состояние упреждающей защиты: `PUBLISH_ENABLED=True`, но публикация всё равно заблокируется, если отсутствуют **обе** настроенные схемы GitHub Actions. Для первого коммита пользовательская фиксированная цель из локального зашифрованного снимка имеет приоритет, затем каноничен последний `owner.enc` из GitHub.

## Безопасность перехода

- Пока `finance/data/family.enc` отсутствует, обе сборки продолжают формировать старый отчёт из Google Sheets. После первой успешной публикации обоих шифротекстов они используют файлы из репозитория и больше не вызывают старый генератор.
- Не менять GitHub Actions вручную и не удалять Google-секреты до проверки развёртывания и всех зависимых сценариев.
- Долги, накопления и исторический дефицит временно наследуются из предыдущего отчёта с отмеченной давностью. Они ещё не сопоставлены с локальным Calc.
- Финансовые данные хранятся в **публичном** репозитории исключительно в шифрованном виде. Защита зависит от стойкости уже существующего пароля; короткие пароли повышают риск перебора при доступном публичном шифротексте. Для долгосрочного использования рекомендованы новые уникальные стойкие пароли и безопасная миграция.

## Тестирование и защита данных

- Регрессионные тесты: `py -m unittest finance.tests.test_calc_publisher`.
- В тестах **синтетические** финансы; пользовательский `.ods` в репозитории не хранится.
- Шифрование: AES-256-GCM, PBKDF2-SHA256, 600 000 итераций. Без парольной защиты финансовые данные в публичном репозитории хранить нельзя. Слабый пароль допускает офлайн-подбор; используется сильный уникальный пароль.
- Сохранённые результаты формул являются снимком последнего **сохранения** книги. Если изменили формулу и не сохранили, Python увидит старое число.
